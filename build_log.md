# Alexis Manosca Build Log

## 1. What I built - and what I deliberately didn't, and why

I built a program that reads the door sensor log and the badge swipe log, corrects for each door's clock offset, and tries to match every door "opened" event to a real badge swipe near it. Where no badge explains an open at a door that's badged in both directions, I flag it. The output is a total count plus a door-by-date table of these flagged events, so someone can go straight to the specific doors and days worth investigating.

I deliberately kept the matching itself simple. Badges are matched to doors greedily (nearest unclaimed badge wins), and I don't use the closed events or open-duration at all, since the sensor log drops too many of them to trust. Since the data is thin and noisy, I chose one explainable rule I could justify and check by hand. I chose this method because there were too many uncertainties in the data and I would rather have tailgating incidents that I missed rather than have too many false positives. This is because I didn't want to saturate the output of this program and make sure that all predicted tailgating incidents are likely to be tailgating, and not wrongly accusing incidents.  

## 2. Assumptions I made where the brief was ambigious

- **Each door's clock has a fixed offset that I correct before matching, found by searching for the offset that lines up the most events.** My first attempt used a symmetric 15 second window on the raw timestamps, on the assumption that the gap was human latency, the time between someone scanning their badge and pushing the door. Measuring the data disproved that. The median badge-to-open gap is negative on several doors (D13 −36s, D10 −34s, D15 −24s), and a person cannot open a door before they scan. The gap is therefore clock skew, not behaviour, which matches the site note that device clocks are set manually and not centrally synchronised. My first attempt at correcting for it took each door's offset as the median gap between an "opened" event and its nearest granted badge event. That worked for quieter doors, but broke badly on D01 (Main Entry, ~300 opens/day). With badges arriving every few minutes, the badge nearest in time to any given door open is very often a coincidentally close but unrelated one, which drags the median toward small, misleading values instead of D01's real offset, matching almost none of D01's events even after "correction". I replaced the median with a direct and brute force search. For each door, try every integer offset in a wide range (-180s to +180s) and keep whichever one puts the most door events within the match window of a badge. That finds one clean, stable offset per door — including D01 at −91s, which alone explains 99.9% of its door events — with no need to treat directions or days separately.

- **After correcting for offset, a door event must fall within a tight window of a badge event to be valid.** With the per-door offset removed the remaining gap is genuine latency plus sensor delay, so a much tighter window (+-5s) is appropriate. Anything outside it is treated as unmatched.

- **Badge events can only validate one door event.** Once a badge event validates the closest door event, it cannot be used to validate another door event, even if that door event also falls within the window. This is what makes a tailgated entry visible: the second person through has no badge left to claim. I match greedily — nearest unclaimed badge first — rather than solving for a globally optimal assignment, which I assumed is close enough for this data.

- **A matched door event inherits the direction of its badge and an unmatched open at an entry-only door is presumed to be an exit.** Door events record only opened/closed and don't say whether it's an entry or exit So where a door event matches a badge I take the badge's stated direction as true, and where it doesn't I fall back to the door's configuration. Doors D04–D16 have push-bar exits, so leaving them legitimately produces an open with no badge. I note that this assumption is exactly what makes tailgating hard to see, since a tailgated entry and a push-bar exit produce identical records.

- **The sensor log drops events, so I ignore "closed" events entirely.** I considered using open/close pairs to find doors held open long enough for a second person to follow through. The data does not support it. There are roughly 2,483 opens with no intervening close, but also roughly 1,611 closes with no preceding open, spread in similar proportion across every door. That symmetry is the signature of random event loss rather than doors genuinely standing open, so I treat unpaired events as logging artifacts and ignore open duration.

- **Only entries can be tailgated.** Doors D04–D16 are entry-only with push-bar exits, so an unbadged exit is expected behaviour and carries no information. Restricting detection to inbound passage removes a large volume of legitimate events from consideration. At D01, D02, D03 and D17 both directions are badged, so an unbadged open there is anomalous either way.

- **A denied badge does not unlock the door.** There are 177 denied badge events. A door opening shortly after a denied badge, with no granted badge nearby, means someone was refused and got in regardless. I treat this as a separate and stronger finding than ordinary tailgating.

## 3. How I used AI - where it went wrong, what I rejected or corrected

I mainly used AI (Claude Code to be specific) as a tool to understand, summarise, and to test the problem at hand. Because the dataset was large, it will take a lot of time for me to go through each entry manually. I used AI to scan the dataset, look for any outliers or interesting records for me to latch onto. This helped me understand the context of the problem and plan my next steps.

Once my planned has been completed, I used AI to generate code to process the information. I specifically worded my prompts how I would write the code myself. This guides the agent to code exactly how I wanted it to.

Because there is no right way to solve this problem, the agent had a tendency to overcomplicate the solution. It tends to dig itself into a hole of solving a specific issue and doesn't realise that it wouldn't matter in the first place. For example, while deciding whether or not I should figure out how to determine whether an open door event was an entry or exit, it suggested multiple solutions on how to determine it. With more analysis, I assumed that it would be best to assume that every badge event is true because the problem that I am trying to solve is tailgating, not whether someone authorised is letting someone inside the building. While that may be a serious problem, I believed it was outside the scope of this solution.

A concrete example of the agent overcomplicating things: when D01 kept showing an implausibly high rate of unexplained door opens even with the fixed clock offset applied, our first hypothesis was that D01 has two independently-drifting reader clocks (in vs out) and possibly a clock reset between weekdays and weekends, so I had it compute the offset per door, per direction, and per day. That doubled the complexity of the offset logic for a result that turned out to be wrong — a quick brute-force check (searching every candidate offset and counting how many events it explains) showed a single, unsplit offset for D01 explained 99.9% of its events. The real problem was in how the offset was being *estimated* (nearest-neighbour median, which is biased on busy doors), not in the model needing to be more granular. I rejected the direction/day-split version and had the agent replace the estimator instead, which turned out to be simpler and correct.

## 4. How I know it works - validation, edge cases, known failure modes

I built a synthetic dataset (test_door_events.csv, test_badge_events.csv, kept in the repo) covering every door in site_description.md, since the real data has no label to help determine whether an event is an example of true tailgating or not. For each of the 17 doors it seeds 9 normal, fully-explained badge+door-open pairs, plus exactly 1 deliberate tailgating incident, a legitimate badge+open, immediately followed by a second "opened" event with no badge at all (the tailgater slipping through). That's 17 seeded tailgating incidents total, spread one-per-door across every door type on site.

Running the program against this set flags exactly 4 unvalidated events — one each at D01, D02, D03 and D17, with every other door at zero. Despite this error, it's the expected result given my own assumptions. Those four are the only doors badged in both directions, so an unmatched open there can only be an anomaly. The other 13 doors are entry-only with push-bar exits, so my model assumes any unmatched open is a legitimate exit. It structurally cannot tell their seeded tailgater apart from someone leaving normally, even though I know it's there because I put it there.

The test doesn't prove the tool catches tailgating in general. It proves it catches every seeded incident exactly where my own assumptions say it can, and misses every one exactly where they say it can't. That's the known failure mode this whole approach contains due to the nature of the door and its data collection system. Tailgating at an entry-only door is invisible to a system that only logs door position and one-way badges, not just to mine.

## 5. What I'd do next time with more time

With more time, the first thing I'd get is labelled data, a stretch of time where someone actually confirmed which door opens were tailgating and which weren't. Right now I have no source of truth to measure against. My synthetic test only checks that the tool catches incidents I planted myself, not how well it performs on real tailgating. Once labelled data existed, a machine learning model trained on it would be worth trying. However, without labels, a model would just be re-learning the same rules I already coded by hand.

I'd also treat the entry-only door blind spot the test brought up as a data collection problem. An unbadged open at a push-bar door is indistinguishable from a legitimate exit with the data as it stands. No amount of logic and reasoning would fix this issue. It would need a reader on the exit side, or a sensor that can tell how many people passed through rather than just open/closed.

I'd also fix the sensor drop-out I had to design around instead of ignore. Door "opened" and "closed" events don't reliably pair up (roughly 2,483 opens with no matching close, and 1,611 closes with no preceding open), which is why I couldn't use how long a door stood open as a signal. More reliable event delivery would give me the chance to do detection I currently can't do at all, like flagging doors propped open long enough for someone to follow through unnoticed.

Better visualisations of the raw data would also have sped up the investigation itself. A lot of the clock-offset and D01 debugging in section 3 was done by eyeballing printed numbers using AI.
